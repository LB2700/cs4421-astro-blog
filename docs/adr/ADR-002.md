# ADR 0001: Use Supabase for application data services

- **Status:** Accepted
- **Date:** 2026-10-07

## Context

Wind Ups is a discussion forum. Its first planned feature is user accounts, followed by user-created posts, agree/disagree responses, and user uploads. Uploads may include both files/media and structured data.

The site needs a relational database for accounts, posts, and votes, as well as file storage. A separate document database was considered for flexible uploaded data, but would add another service, credentials, and cross-database consistency complexity.

The initial service should have a free plan suitable for development and an early prototype. The application runtime is planned as an Astro SSR application and backend in Docker and is hosted separately from the existing static site. Existing AWS S3 and CloudFront static hosting remains unchanged.

## Decision

Use Supabase for managed PostgreSQL, user authentication, and object storage. Store profiles, posts, votes, and upload metadata in a PostgreSQL schema.

- Relate profiles to Supabase Auth identities without making application code depend on Supabase's internal Auth tables.
- Store posts and individual agree/disagree votes in PostgreSQL.
- Store modestly variable structured uploads in PostgreSQL JSONB when they need database querying.
- Store uploaded files and media in private Supabase Storage buckets, with ownership and object metadata in PostgreSQL.
- Use Row Level Security (RLS) and server-side authorization to enforce access.
- Manage database schema and database-level policies as code using version-controlled Supabase CLI SQL migrations. Treat committed migrations as the source of truth; do not make untracked schema changes directly in the hosted dashboard.

Do not add a separate document database unless measured requirements show that PostgreSQL tables and JSONB cannot meet the structured-upload query or scale needs.

## Database configuration as code

Store schema changes, constraints, indexes, and RLS policies in ordered SQL migration files under `supabase/migrations/`. Use the Supabase CLI to apply and test migrations against a local Supabase stack before deploying them to a linked hosted project. Keep seed data separate from schema migrations, and do not include production data or credentials in the repository.

Use the Supabase dashboard for project administration and settings that are not represented by database migrations, such as managing project access and configuring Auth providers or redirect URLs. Where supported, keep project configuration in the CLI's `config.toml`; treat secrets as environment-specific values managed outside Git. The dashboard is not the source of truth for database schema: if an urgent schema change is made there, capture it in a migration and commit it before making further schema changes.

## Alternatives considered

### Configure the database directly in the Supabase dashboard

The dashboard is convenient for exploration and one-off inspection, but undocumented manual changes can cause local, staging, and production databases to diverge. It does not provide the same reviewable history or repeatable setup as committed migrations, so it is not the normal schema-change workflow.

### Neon PostgreSQL

Neon provides managed PostgreSQL and is a viable free-plan alternative. Neon also offers managed authentication and object storage, but these have different integrations and workflows from Supabase Auth and Storage. Supabase was selected because of prior experience with it.

### PostgreSQL plus a document database

This could suit future workloads with distinct document-query requirements. At the current stage, it adds extra operational and authorization complexity without any immediate benefit. Reconsider if real structured-upload access patterns justify the extra service.

### Self-managed PostgreSQL

Running and operating PostgreSQL alongside the Docker application offers control but adds deployment, backups, upgrades, monitoring, and recovery responsibilities. This is unnecessary for the initial prototype.

## Consequences

### Pros

- One provider covers the initial relational data, authentication, and uploaded-file needs.
- PostgreSQL constraints and transactions suit account relationships and vote integrity.
- JSONB supports flexible records without committing to another database.
- Versioned SQL migrations provide a reviewable history and repeatable schema setup across development and hosted environments.
- The application can begin on a free plan and scale or migrate as actual usage becomes clear.
- Can switch to another service provider/self hosted Postgres database if I chose to do so.

### Cons

- Supabase CLI migrations and configuration-as-code do not capture every dashboard setting or external service configuration; those settings need their own documented and environment-aware management.
- Direct dashboard schema changes can create drift if they are not promptly captured in a committed migration.
- Supabase-specific Auth, Storage, RLS identity helpers, and APIs create service-specific migration work. PostgreSQL compatibility does not make those services automatically portable.
- Free-plan capacity, availability, pauses, backups, and support are limited and may change. Keep independent exports and confirm current terms before production use.
- A later Auth migration may require account recovery or password resets; database migration alone does not migrate identity behavior or sessions.
- File objects are not included in PostgreSQL backups. They and their metadata must be copied separately, including any changes to object keys or URLs.

## Migration considerations

Keep domain access in the Docker backend and use standard PostgreSQL tables, constraints, indexes, and JSONB where practical. Avoid relying on Supabase internals in application queries. If moving providers, rehearse a migration of the application's schema and data, separately plan Auth and Storage migration, validate authorization at the destination, and switch configuration only after verification. A PostgreSQL dump does not by itself migrate users, uploaded objects, or Supabase policies and service behavior.
