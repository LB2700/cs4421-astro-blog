#ADR-001: Transition from Static Site to Containerized SSR Runtime

## Status: Accepted (Date: 2026-10-06)

## Context
Wind Ups requires dynamic API endpoints. Static hosting on S3 cannot execute server-side Node.js code. Wind Ups requires a site that feels interactive.

Future features like, user authored content, user authentication, personalization, and feedback collection are not feasible without architectural changes.

### Pros
 - **Real-time Data:** Support live user sessions, feedback collection, and dynamic content without rebuilds. 
 - **Foundation for Auth:** Prepares architecture for user authentication, session management, and protected pages.
 -  **Backward Compatibility:** All existing static content routes remain functional; no breaking changes for readers.

### Cons
 - **Compute Costs:** Transition from SSG to SSR increases infrastructure costs
 - **Operational Complexity:** Requires container orchestration, health monitoring, server logging and database management.
 - **Server Dependency:** Application availability now depends on server uptime; SSG provided passive fault tolerance via static files.
 - **Latency** Page generation latency per-request may exceed SSG responses.
 - **Database Connection:** Future features will require persistent database connections, introducing state management concerns.

## Decision
We will configure Astro with the `@astrojs/node` adapter in standalone mode
and package the application as a Docker container.

## Consequences
- Positive: Enables live API routes, dynamic rendering, and operational health checks.
- Negative: Increases operational complexity; requires container compute runtime.
