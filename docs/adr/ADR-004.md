# ADR-004: Track Supabase schema with CLI migrations

- **Status:** Pending
- **Date:** 2026-10-20

## Context

The database schema and Supabase configuration need to be reproducible across development and test environments. Managing schema changes only through the dashboard makes those environments difficult to recreate consistently and can lead to schema drift.

Integration tests need a predictable database state, including tables, constraints, triggers, and Row Level Security policies. They must not depend on production data.

## Decision

Use the Supabase CLI and version-controlled database migrations to manage schema changes. Capture schema updates as migrations and commit them with the application code. Use seed files for synthetic test data where needed.

## Consequences

- A developer or CI job can start a disposable local Supabase environment and apply the same migrations used to define the project schema.
- Integration tests can reset the test database to a known state, apply migrations, load synthetic fixtures, run tests, and discard the environment without copying production records.
- Schema changes become reviewable and can be applied consistently to development, staging, and production.
- Dashboard-only changes must be captured in migrations to avoid schema drift. Project-level settings such as SMTP and Auth redirect URLs may still require separate configuration.
- Local integration tests require the Supabase CLI and its container runtime.
